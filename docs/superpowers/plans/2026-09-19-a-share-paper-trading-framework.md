# A 股模拟交易框架与实施步骤

## 实施状态（2026-09-19）

第一版核心 MVP 已实现：领域模型、SQLite 账本、现金与持仓流水、交易意图、硬性风控、人工审批、幂等订单、T+1 结转、费用与滑点、下一行情模拟撮合、腾讯 Level 1 实时盘口适配、账户摘要、对账、一键停止、命令行入口和可选 vn.py PaperAccount 安全边界。

已通过 27 项项目测试，其中 7 项为模拟交易专项测试；真实行情冒烟测试确认非交易日和过期行情会拒绝交易且不会创建订单。

尚未启用正式模拟账户配置，也未安装 vn.py 可选依赖。后续剩余工作是：由用户确认资金和风控阈值、接入正式交易日历、完成 vn.py 事件同步、在简报页面展示模拟账户摘要，并进行影子运行。详细使用方法见 `docs/paper-trading-quickstart.md`。

## 1. 目标

在现有 A 股持仓简报自动化之外，增加一个独立、可审计、默认半自动的模拟交易系统。系统读取行情、简报信号和账户状态，生成交易意图，经过硬性风控和用户确认后提交到本地模拟账户，记录订单、成交、持仓、现金、费用和复盘结果。

首版只做模拟交易，不连接真实券商资金账户，不提供切换实盘的配置开关。

## 2. 采用方案

- 核心交易框架：[vnpy/vnpy](https://github.com/vnpy/vnpy)
- 本地模拟账户：[vnpy/vnpy_paperaccount](https://github.com/vnpy/vnpy_paperaccount)
- 现有项目继续负责行情、公告、估值、申万行业和简报生成。
- 新增独立的模拟交易领域层，避免业务逻辑直接依赖 vn.py；未来替换撮合器或接入其他纸面账户时，不改策略和风控。
- Python 使用现有专用环境的 3.12 版本，但模拟交易依赖单独锁定，不直接污染日报的稳定依赖集合。

## 3. 明确边界

### 本期范围

- A 股普通股票的本地模拟买卖。
- 限价委托；市价意图必须在执行层转换成带价格保护的限价单。
- 账户现金、冻结资金、可用持仓、当日买入、累计盈亏和费用记录。
- 半自动审批：系统提出交易，用户批准后才可提交。
- 硬性风控、幂等下单、完整审计日志、每日对账和复盘。
- 在 HTML/PDF 简报中只展示模拟账户摘要和待审批建议，不从报告渲染函数直接下单。

### 暂不实现

- 真实券商或真实资金账户。
- 融资融券、期权、期货、可转债申购和新股申购。
- 做空、杠杆、跨账户资金调拨。
- 高频、集合竞价和夜间自动委托。
- 让语言模型直接修改风控配置或绕过审批。

## 4. 总体架构

```text
腾讯/AKShare/公告/申万数据
            │
            ▼
    现有 A 股持仓简报
            │
            ▼
      SignalIntent 交易意图
            │
            ▼
      硬性规则风控引擎
       │通过       │拒绝
       ▼           ▼
Approval Pending  RiskRejected
       │
       ▼ 用户明确批准
   Order Service ──幂等键/状态机/审计──┐
       │                              │
       ▼                              ▼
vn.py PaperAccount               SQLite Ledger
       │                              │
       └────成交、持仓、现金回报────────┘
                       │
                       ▼
```

核心原则：语言模型只能提交结构化交易意图，不能直接写账户余额、成交和持仓；账户状态只能由订单服务依据成交事件更新。

## 6. 核心数据契约

### 6.1 SignalIntent

策略和简报只能生成意图，不能直接生成成交：

```json
{
  "intent_id": "20260919-002195-buy-001",
  "created_at": "2026-09-19T09:20:00+08:00",
  "strategy_id": "brief_signal_v1",
  "symbol": "002195.SZ",
  "side": "BUY",
  "quantity": 100,
  "limit_price": 6.05,
  "valid_until": "2026-09-19T10:00:00+08:00",
  "reason_codes": ["price_above_ma20", "industry_strength"],
  "evidence_snapshot_id": "snapshot-uuid",
  "requires_user_approval": true
}
```

必须字段：唯一意图 ID、生成时间、策略版本、证券代码、方向、数量、限价、失效时间、结构化理由和证据快照。缺一项即拒绝。

### 6.2 RiskDecision

```json
{
  "intent_id": "20260919-002195-buy-001",
  "decision": "APPROVAL_REQUIRED",
  "checked_at": "2026-09-19T09:20:01+08:00",
  "ruleset_version": "risk-v1",
  "checks": [],
  "rejection_reasons": []
}
```

风控结论只能为 `APPROVAL_REQUIRED`、`APPROVED` 或 `REJECTED`。每次检查保存规则版本、输入快照及逐条结果。

### 6.3 Order 与 Fill

- `Order` 保存客户订单号、意图 ID、审批人/审批时间、状态、限价、数量、已成交数量、拒绝原因和适配器订单号。
- `Fill` 保存成交编号、订单号、成交时间、价格、数量、佣金、印花税、过户费、滑点和行情快照 ID。
- 订单与成交必须追加记录，不通过覆盖历史字段隐藏状态变化。

## 7. 订单状态机

```text
PROPOSED
  ├─风控拒绝──────────────> RISK_REJECTED
  └─风控通过──────────────> APPROVAL_PENDING
                                ├─用户拒绝──> USER_REJECTED
                                ├─超时──────> EXPIRED
                                └─用户批准──> APPROVED
                                                  │
                                                  ▼
                                              SUBMITTED
                                         ┌────────┼────────┐
                                         ▼        ▼        ▼
                                  PARTIALLY_FILLED FILLED REJECTED
                                         │
                                         ├────────> FILLED
                                         └────────> CANCELED
```

只有 `APPROVED` 可以进入 `SUBMITTED`。同一 `intent_id` 和 `client_order_id` 重复调用必须返回原订单，禁止重复下单。

## 8. A 股交易规则处理

- 买入数量按交易单位校验；默认普通股票买入为 100 股整数倍。
- 卖出检查可用数量及 T+1，不能卖出当日买入且尚不可用的股份。
- 不在代码中永久写死涨跌幅限制、交易状态和费用政策；由证券主数据和配置提供，并记录生效日期。
- MVP 只接受连续竞价时段，排除集合竞价；午间休市、节假日、停牌时拒绝提交。
- 涨停时不假设买入一定成交，跌停时不假设卖出一定成交。
- 行情超过配置的最大时延时拒绝交易，不能用日报价格冒充实时下单价。
- 市价意图转换为有最大滑点保护的限价委托。
- 费用模型可配置，并保存配置版本；费用变化不得改写历史成交。

## 9. 硬性风控

以下检查在 Python 代码中执行，不交给模型自由判断：

1. `paper_mode` 必须为真，并且适配器必须是允许名单中的模拟适配器。
2. 存在 `runtime/paper_trading/kill_switch` 时禁止新单，只允许撤单和查询。
3. 标的必须位于用户配置的股票白名单。
4. 行情新鲜度、交易日、交易时段、停牌和涨跌停状态通过。
5. 数量、价格、交易单位和最小价格变动合法。
6. 单笔金额、单股市值、行业集中度和总仓位不超过配置上限。
7. 买入后现金不得低于安全垫，卖出不得超过可用持仓。
8. 当日亏损或回撤超过阈值后禁止开新仓。
9. 同方向冷却时间内的重复意图拒绝。
10. 证据快照、策略版本或风控配置缺失时拒绝。
11. 首版所有订单必须有未过期的人工批准记录。

风险阈值不在框架中擅自确定。初始化时要求用户明确填写本金、单笔上限、单股上限、总仓位上限、日亏损上限、允许标的和最大行情时延。

## 10. 模拟撮合规则

- 以收到委托后的下一条合格行情作为最早可成交时点，防止使用已知价格回填成交。
- 买单只有在行情卖价不高于限价时才可成交；卖单只有在行情买价不低于限价时才可成交。
- 无五档数据时使用保守滑点模型，不直接按最新价全额成交。
- 支持部分成交，剩余数量继续等待或按有效期撤销。
- 成交量不能超过配置的行情可成交比例。
- 停牌、无行情、行情过期、触及不可成交状态时保持挂单或拒绝，不伪造成交。
- 每次撮合保存输入行情快照、模型版本及计算结果，确保可复算。

## 11. 数据存储与审计

使用 SQLite，所有账户变更放在单个事务内。建议表：

- `accounts`：初始资金、可用现金、冻结现金、状态。
- `positions`：总持仓、可用持仓、冻结持仓、成本、当日买入。
- `intents`：模型或规则产生的交易意图及证据引用。
- `risk_decisions`：逐次风控检查和规则版本。
- `approvals`：批准、拒绝、操作者和时间。
- `orders`、`order_events`、`fills`：订单状态与成交事件。
- `cash_ledger`：每笔现金变动，余额由流水核对。
- `position_ledger`：每笔持仓变动。
- `market_snapshots`：下单和成交使用的行情证据。
- `daily_snapshots`：每日权益、现金、仓位和盈亏。

数据库启用外键、WAL、事务和唯一约束。日志中不得出现 API 密钥；运行配置和账户快照每日备份，但密钥不进入备份。

## 12. 与现有简报的集成方式

1. `generate_600601_report.py` 保持只读，不直接导入 vn.py 下单函数。
2. 简报在完成数据校验后，可以额外生成 `SignalIntent` 候选文件。
3. `signal_adapter.py` 校验候选文件并写入账本，状态为 `PROPOSED`。
4. `risk_engine.py` 生成风控结论；通过后显示在 HTML 的“模拟交易待审批”区域。
5. 用户批准通过独立命令或本地界面写入审批记录，不修改原始意图。
6. 独立执行器读取 `APPROVED` 订单并提交模拟账户。
7. `report_adapter.py` 只读账户快照，向下一期简报提供现金、持仓、当日盈亏、累计盈亏和未完成订单。

这条隔离线必须保留：报告生成失败不能影响账户，报告文本也不能成为可直接执行的命令。

## 13. 实施步骤

### Phase 0：固定安全边界与依赖

- [ ] 新建功能分支或独立工作区，不在定时任务运行期间直接改生产脚本。
- [ ] 固定 `vnpy` 和 `vnpy_paperaccount` 版本，验证 Python 3.12 安装兼容性。
- [ ] 为模拟交易建立独立 requirements/lock 文件。
- [ ] 配置目录和运行数据目录加入 `.gitignore`，密钥文件永不提交。
- [ ] 写一项启动测试，证明不存在真实券商适配器和实盘开关。

验收：安装模拟依赖不影响现有简报的 20 项测试及输出回归。

### Phase 1：领域模型和 SQLite 账本

- [ ] 创建 `models.py`，实现证券、交易意图、风控结论、订单、成交、持仓和账户快照。
- [ ] 创建 `ledger.py` 和数据库迁移脚本。
- [ ] 实现现金流水与持仓流水的双向核对。
- [ ] 增加唯一键：`intent_id`、`client_order_id`、适配器成交号。
- [ ] 写并发和崩溃恢复测试，确认一次事务只产生一次余额变化。

验收：用固定成交样本可从流水重建出完全一致的现金、持仓和总资产。

### Phase 2：PaperBroker 抽象和确定性假适配器

- [ ] 定义 `PaperBroker` 接口：账户查询、订单提交、撤单、订单查询、成交同步和行情订阅。

验收：同一订单重复提交 100 次，账本中仍只有一笔有效委托和一组对应成交。

### Phase 3：A 股规则和风控引擎

- [ ] 将交易日、连续竞价时段、T+1、交易单位、价格边界和行情时延实现为独立规则。
- [ ] 实现资金、仓位、行业集中度、日亏损、白名单和冷却期规则。
- [ ] 实现 kill switch，并保证重启后仍生效。
- [ ] 每条风控规则写通过、拒绝和边界值测试。
- [ ] 对配置缺失采用 fail-closed：拒绝交易，而不是给默认宽松值。

验收：任何一项必要数据缺失、过期或不合法时都无法进入 `APPROVED`。

### Phase 4：本地撮合和费用模型

- [ ] 实现下一行情撮合、限价条件、部分成交、滑点和成交量上限。
- [ ] 实现可版本化费用配置，覆盖买入、卖出和最低佣金情形。

- [ ] 保存每次成交对应的行情快照和撮合版本。

验收：所有成交都能依据保存的行情和配置离线复算，误差为零。

### Phase 5：接入 vn.py PaperAccount

- [ ] 实现 `VnpyPaperAdapter`，把内部订单模型映射为 vn.py 请求。
- [ ] 监听委托、成交、账户和持仓事件，转换成内部事件后写入账本。
- [ ] 启动时先同步 vn.py 状态，再允许接受新单。
- [ ] 对适配器断线、重连、重复事件和乱序事件做测试。
- [ ] 适配器返回与内部账本不一致时触发只读安全模式。

验收：固定行情回放中，内部账本与 PaperAccount 的订单、成交、现金和持仓完全一致。

### Phase 6：接入简报信号

- [ ] 定义简报信号到 `SignalIntent` 的明确映射，避免把自然语言段落直接当订单。
- [ ] 为每个意图保存触发指标、来源时点、策略版本和简报证据快照。
- [ ] 第一版只允许白名单标的，且只生成 `APPROVAL_PENDING`。
- [ ] 在 HTML 中增加待审批、已拒绝、已成交和账户摘要；PDF 只展示摘要。
- [ ] 数据源处于 `DEGRADED` 且涉及交易关键字段时，禁止生成可批准意图。

验收：简报可以没有交易意图，但任何交易意图都必须可追溯到结构化证据。

### Phase 7：审批、运行脚本和自动化

- [ ] 建立初始化、提议、批准、拒绝、执行、撤单和对账命令。
- [ ] 审批命令展示代码、名称、方向、数量、限价、预计金额、风控占用和理由。
- [ ] 审批必须引用精确 `intent_id`，并在有效期内完成。
- [ ] 执行器单实例运行，使用进程锁防止定时任务重叠。
- [ ] 未批准、已过期或风控配置发生变化的意图不得执行，需重新检查。

验收：定时任务只能推进已批准订单；没有用户批准时，账户零交易。

### Phase 8：试运行和放行标准

- [ ] 使用历史行情回放至少 20 个交易日。
- [ ] 使用实时行情影子运行至少 10 个交易日，仅生成建议、不提交。
- [ ] 再运行至少 10 个交易日的小规模模拟成交。
- [ ] 每日核对订单、成交、现金、持仓、费用和权益。
- [ ] 统计拒单原因、滑点、成交率、最大回撤、策略换手和数据降级次数。
- [ ] 完成 kill switch、断网、重复启动、数据库锁和行情过期演练。

放行条件：无重复单、无负现金、无超卖、无账实差异、所有成交可复算、所有订单都有风控和审批记录。

## 14. 测试矩阵

| 场景 | 预期结果 |
|---|---|
| 相同意图重复提交 | 返回原订单，不新增委托 |
| 行情过期 | 风控拒绝 |
| 非交易时间 | 风控拒绝 |
| 当日买入后卖出 | T+1 规则拒绝 |
| 数量不是合法交易单位 | 风控拒绝 |
| 现金不足或超过仓位限制 | 风控拒绝 |
| kill switch 存在 | 禁止新单 |
| 用户未批准或批准已过期 | 禁止提交 |
| 部分成交后重启 | 恢复剩余数量，不重复成交 |
| 适配器事件重复或乱序 | 幂等处理并保持账本一致 |
| vn.py 与本地账本不一致 | 进入只读安全模式并告警 |
| 简报关键数据降级 | 不产生可批准交易意图 |

## 15. 首个 MVP 的完成定义

- 初始化一个用户指定本金的本地模拟账户。
- 仅允许用户明确配置的 A 股白名单。
- 系统可从结构化输入生成一笔买入或卖出建议。
- 所有风控通过后进入待审批状态。
- 用户明确批准后，模拟账户完成提交、撮合、记账和回报。
- HTML 展示现金、持仓、成本、当日/累计盈亏、未完成订单和最近成交。
- 重启后状态完整恢复；重复执行不会重复下单。
- 一键停止有效，运行日志不包含密钥。
- 现有简报自动化及测试保持通过。

## 16. 实施顺序建议

先完成 Phase 0–4，用确定性假行情把账本、风控、状态机和撮合测试透彻；再接 vn.py。不要先接实时行情或做策略优化，因为交易系统最难修复的问题通常是重复下单、账本不一致和风控失效，而不是信号本身。

首个可用版本完成后，默认仍保持半自动。只有影子运行和模拟成交达到 Phase 8 的放行条件，才讨论是否允许在严格边界内自动批准模拟订单；实盘连接不属于本计划。
